# Design

## Context

多模型评审已按主规范 `multi-model-review` 交付:`ocr_ext review` 将主模型与每条 reviewer 各派发为一个标准 `ocr review` 子进程,确定性合并(位置 IoU + 内容相似度双条件,零 LLM 调用),`found_by` 归因与 `sources` 统计已落地。实际使用暴露出两个结构性短板:确定性合并对"措辞差异大的同题发现"无能为力(宁多不丢的既定盲区);主模型亲自下场评审却没有裁决角色,同名模型走不同线路(配额容灾的正当需求)被重名检查拒绝。用户明确的架构诉求:主模型转为**协调者**——不评审,负责对合并结果做语义去重并统一产出报告。动机与探索过程见 proposal.md。

架构事实(已在实施中验证):reviewer 子进程经 `--config` 临时配置获得各自端点;确定性合并、collapse 规则、`found_by` 归因在 `internal/merge`;`extractTopLevelJSON` 可从 `internal/llmloop` 复用;主模型端点可由父进程经 `llm.ResolveEndpointWithOptions` 取得,协调调用直接复用 `llm.NewLLMClient`。

## Goals / Non-Goals

**Goals:**

- 角色分离:有 reviewers 时主模型只协调不评审;无 reviewers 时单模型路径字节级不变。
- 语义去重:主模型对确定性合并的盲区(措辞差异大的同题发现)做分组裁决,代码按裁决执行合并。
- 零幻觉面:主模型只能输出编号分组,不能改写、发明或删除发现内容;校验失败即回退。
- 失败韧性:协调任何环节失败(网络、配额、输出不合法、退化输出)都回退到确定性结果,exit 码不变。
- 可审计:`coordination` 元数据块记录协调是否发生、模型、分组数、token 用量。

**Non-Goals:**

- 调度保持代码确定性:不做 LLM 任务分配(按主题给 reviewer 派活),不引入派发前的串行规划阶段——全量并行保证覆盖,Phase 2 另议。
- 主模型不重写报告文本:报告内容逐条来自真实 LLM 输出,主模型只决定分组。
- 不做独立裁判模型字段(协调固定用主模型端点),后续可增量。
- 不做协调结果的流式输出;单次尝试不重试。
- 不做 `ocr_ext scan` 的协调化;单模型路径(无 reviewers)行为不变。

## Decisions

### D1: 主模型角色切换与编排形态

配置了 reviewers 时,子进程只有 reviewers(N 路并行);主模型不再派发评审子进程。全部子进程结束后:确定性合并(骨架)→ 触发判断 → 协调调用 → 校验与合并 → 最终报告。无 reviewers 时主模型作为唯一评审路执行完整单模型评审:整条命令**原样委托**给 `ocr review`——stdout/stderr 直通、退出码透传、不添加任何前缀或包装,行为与输出与直接运行 `ocr review` 完全一致。来源前缀只属于多模型编排(≥2 路并行时用于归属)。备选的"主模型评审兼协调"被否决:协调者自己有发现待裁决,自裁偏见无法根除;备选的"主模型评审 session 内连续协调"(多智能体对话)工程量大,列为 Phase 2。

### D2: 协调契约——分组断言,不是报告生成

协调调用是**一次普通补全**(复用 `llm.NewLLMClient`,非流式):输入为编号发现清单(路径:行号、severity、category、内容单条截断 600 字符),指令要求输出严格 JSON 的数组的数组——每内层数组是一组"描述同一问题"的编号。主模型**不被允许也不被需要**输出任何发现文本。备选的"主模型直接重写最终报告"被否决:报告内容将依赖一次 LLM 输出的忠实性,幻觉与丢发现风险不可控,且破坏 JSON 契约。输入不含 diff 全文:判断同题只需发现自身信息,避免 prompt 膨胀与明文 http 传输扩大。

### D3: 输出校验与消解

解析链:`extractTopLevelJSON`(复用 `internal/llmloop`)抠 JSON → 解析为 `[][]int` → 逐元素校验为界内整数 → **任一编号越界或 JSON 不可解析即整体回退**(严格式;部分容忍可能产出诡异的合并) → 对合法的"同组"断言建 union-find,闭包消解重叠分组(主模型无需保证分组互斥)→ 未覆盖编号为单元素组 → 每组经既有 collapse 收敛。熔断:任一闭包后分组吸收超过输入总数 60% 的发现,判定退化输出,整体回退。

### D4: 同名模型放开与消歧

`found_by` 键为来源名。同名模型不同端点的多路并行被允许;归因时对重名追加 `@<host>` 后缀(host 取该来源配置的 URL host)。两条规则随之调整:与协调者端点+模型相同的条目**不再丢弃**(协调者不评审,无重复劳动);彼此端点+模型完全相同的条目保留首个、丢弃后续(真正的重复)。协调者不产发现、不进任何 `found_by`,也不出现在 `sources` 块——其记录统一在 `coordination` 元数据块。消歧粒度为 host:同 host 不同路径的同名模型极端配置下仍可能重名,实现以归一化 URL 兜底。

### D5: 失败语义与熔断

reviewer 子进程失败 → 警告 + 其余照常(沿用);全部 reviewer 失败 → 报错退出(沿用,此时无协调对象);协调阶段任何失败(调用错误、JSON 不合法、退化输出)→ 回退确定性结果 + warning,exit 0。协调调用单次尝试不重试:回退产物本身可用,重试是延迟税。

### D6: 配置与开关

`coordination` 开关由 `ocr_ext` 自解析(轻量 struct,与 reviewers 同路径;`ocr` 侧 `Config` 不加字段——跨 main 包不可用且无必要,混版本保护由既有 `unknownJSONFields` 机制承担)。缺省视为 `true`;`false` 时不发起协调调用,多模型行为回退为纯确定性合并(即本次变更前的行为)。开关只影响协调阶段,不影响派发与确定性骨架。

### D7: 报告形态

`mergedOutput` 新增 `coordination` 块(`ran`/`model`/`groups`/`input_findings`/`tokens`);`sources` 仅含 reviewer 行(`role: reviewer`),协调者的记录统一在 `coordination` 块。text 渲染在尾部追加协调摘要行。单模型路径(无 reviewers)不产出这些块,字节级不变。

## Risks / Trade-offs

- 协调者能力上限 = 主模型能力:flash 级模型分组质量有限 → 主模型应选最强模型(本就是"主模型"的含义);熔断与回退兜底。
- 误合并仍可能发生:主模型把不同问题判为同题 → 组内低 severity 的发现正文被吸收 → 接受(用户明确要求 LLM 去重;`found_by` 并集保留来源线索),提示词写明"不确定就分开"。
- 协调调用走主模型端点:主模型配额耗尽时协调失败 → 回退,多模型退化为纯确定性(发现仍产出)。
- 发现内容经明文 http 发给协调端点 → 与评审请求同级,无新增暴露面。
- found_by 的 `@host` 后缀:下游若对模型名做精确匹配需注意 → 无存量严格消费者,文档标注。

## Migration Plan

纯增量,默认行为即新行为(协调缺省开启):多模型用户升级后自动获得协调去重;不想要者设 `coordination: false` 回到纯确定性。无 reviewers 用户零感知。单模型 `ocr review` 路径零改动。回滚 = `coordination: false` 或回退本 change 提交。

## Open Questions

无——深度一(裁决不改写)、触发边界、熔断、先归档再立项的拓扑、调度保持确定性,均已在探索中与用户确认。
